# BRIDGE-000026 — Live Add-in Loading Without Altium Restart

## 1. Цель

Проверить возможность загрузки диагностического Add-in `EcadMcadBridge.dll` в уже работающий Altium Designer 26.12.2.9 без завершения или перезапуска процесса X2.

Использовать результат для снятия runtime-блокера BRIDGE-000024 и выполнения диагностики BRIDGE-000025.

Оператор отдельно подтверждает:

**Перезапуск основной сессии Altium запрещён. Оператор обеспечит, чтобы процесс X2 не завершался.**

Поэтому агент не должен самостоятельно закрывать, перезапускать или завершать Altium.

Repository: `YOUASSBEE/EcadMcadBridge`

- BRIDGE-000025 HEAD: `40ed61706f6d96f68f89146c4eb9e717aefb5ae5`.
- Altium Designer: 26.12.2.9.

Перед началом проверить актуальные SHA и состояние PR.

## 3. Абсолютные ограничения

Запрещено:

- завершать процесс X2;
- перезапускать Altium;
- закрывать текущую сессию;
- заменять DLL, пока она загружена процессом;
- менять machine-wide каталог расширений;
- менять реестр;
- редактировать постоянные `.ins` и `.rcs`;
- изменять постоянную конфигурацию Altium;
- изменять или сохранять исходный `Dev_board.PcbDoc`;
- изменять production placement;
- менять D-022 или D-024;
- активировать Bottom в production;
- использовать неподдерживаемые API, reflection или Legacy API.

Если для следующего шага требуется завершение X2 или постоянная регистрация расширения — немедленно остановиться.

Не выполнять запрещённое действие даже с согласия на отдельную операцию без нового явного решения Оператора.

## 4. Этап A — обследование работающего процесса

Не изменяя состояние Altium:

1. Зафиксировать PID X2.
2. Проверить путь к исполняемому файлу.
3. Определить фактически загруженные:
   - `EcadMcadBridge.dll`;
   - `EcadMcadBridge.Core.dll`.
4. Зафиксировать их пути, версии, SHA-256 и состояние блокировки файлов.
5. Проверить фактический каталог расширений.
6. Проверить доступность per-user Extensions.
7. Проверить, какие команды реально зарегистрированы в текущей сессии.
8. Подтвердить, что исходная конфигурация не менялась.

Не пытаться разблокировать или заменить загруженные файлы.

## 5. Этап B — исследование поддерживаемых механизмов

Исследовать официально поддерживаемые для Altium Designer 26 механизмы:

1. Динамическая загрузка Add-in в уже работающий процесс.
2. Штатная регистрация дополнительной команды без перезапуска.
3. Per-user расширения или пользовательские каталоги расширений.
4. Поддерживаемый API управления жизненным циклом расширений.
5. Возможность загрузки отдельной DLL без замены уже загруженной.
6. Возможность запуска диагностического кода через существующий зарегистрированный Add-in.

Для каждого механизма установить:

- официальное название;
- интерфейс/API/UI;
- поддерживаемую версию Altium;
- требования к регистрации;
- требуется ли перезапуск;
- меняется ли реестр или постоянная конфигурация;
- можно ли выполнить операцию без завершения X2.

Использовать SDK и официальную документацию Altium.

Не считать `obj_run_process` подтверждением существования команды: ранее Altium возвращал `dispatched=true` даже для неизвестного process name.

Не считать `Client:StartServer/StopServer` механизмом загрузки Add-in.

Не использовать самодельный DLL injection, удалённую загрузку библиотек, изменение памяти процесса или обход механизмов блокировки файлов.

## 6. Этап C — проверка per-user каталога

Отдельно проверить гипотезу о пользовательском каталоге Extensions.

Установить:

1. Существует ли поддерживаемый per-user каталог для AD26.
2. Подхватывает ли текущая установка Altium этот каталог.
3. Можно ли загрузить из него дополнительное расширение в текущую сессию.
4. Требуется ли изменение постоянной конфигурации.
5. Требуется ли перезапуск.

Сам факт существования каталога не означает, что Altium его использует.

Не создавать файлы регистрации и не копировать туда DLL до подтверждения поддерживаемого механизма.

## 7. Этап D — решение о runtime-проверке

Выполнять только если найден поддерживаемый механизм, который одновременно:

- не завершает X2;
- не требует перезапуска;
- не заменяет загруженную DLL;
- не меняет machine-wide регистрацию;
- не изменяет реестр;
- не требует постоянной конфигурации.

Если такой механизм найден:

1. Использовать диагностический код из PR #23.
2. Собрать Release DLL из зафиксированного commit.
3. Зафиксировать SHA-256 обеих DLL.
4. Загрузить расширение поддерживаемым способом.
5. Подтвердить фактическую регистрацию команды.
6. Запустить `ReadBodyIdentityDiagnostics`.
7. Проверить создание `diagnostics.json`.
8. Выполнить проверку 15 designators и 9 Bottom/Top пар согласно BRIDGE-000025.

Если найденный механизм не позволяет безопасно выполнить диагностику, остановиться до изменения состояния Altium и описать ограничение.

## 8. Проверка результата

Успешный runtime результат требует:

- фактического выполнения команды;
- созданного `diagnostics.json`;
- записей по проверяемым объектам;
- статусов доступности полей;
- фактических значений `bodyUniqueId`;
- фактических значений `footprintSourceUniqueId`;
- фактических значений `IPCB_Model.GetOrigin().X/Y/Z`, если API их предоставляет.

`dispatched=true`, `unlisted_process` и отсутствие исключений не являются успехом.

Не подменять ModelOrigin bbox-значениями.

Не генерировать фиктивные идентификаторы.
