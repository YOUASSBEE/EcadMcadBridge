# BRIDGE-000013 — Core: 3D Asset Exchange Package

## 1. Цель

Расширить Core Exchange Package поддержкой трёхмерных моделей компонентов.

Результат — пакет, который может содержать:

- существующий `board.snapshot.json`;
- каталог `models/models.json` с описанием 3D-моделей компонентов и отдельных тел;
- файлы геометрии STEP AP214 и/или Parasolid X_T в `assets/3d/`;
- SHA-256 и размеры всех файлов в существующих `manifest.json` и `checksums.sha256`.

Реализовать полный цикл на стороне Core:

1. Типизированная модель каталога 3D-моделей.
2. Детерминированная сериализация и десериализация каталога.
3. Запись 3D-ассетов в пакет.
4. Чтение и полная проверка каталога и ассетов.
5. Сохранение обратной совместимости с пакетами без 3D-моделей.

**Это задача на контракт данных и Core Packaging, а не на извлечение моделей из Altium.**

## 3. Архитектурные ограничения

Обязательные ограничения:

- Core остаётся независимым от Altium SDK и SOLIDWORKS SDK.
- TFM остаётся `net10.0`.
- Не использовать DelphiScript, Legacy API, reflection или `dynamic`.
- Не создавать проект SOLIDWORKS и не добавлять SOLIDWORKS interop.
- Не выполнять вызовы Altium SDK для извлечения моделей.
- Не менять существующую модель `BoardSnapshot`, если это не требуется для связи каталога с уже существующими компонентами.
- Не менять формат и смысл существующих координат и преобразований.
- Не помещать пользовательские PCB, STEP/X_T и другие бинарные CAD-данные в Git.
- Не сохранять абсолютные исходные пути в JSON, manifest и диагностике.

PR #9–11 показывают, что геометрия, положение компонента и состояние модели — разные сущности. Не объединять их в одну матрицу без подтверждённой математической модели.

**Запрещено выводить неподтверждённые значения Z, зеркальное отражение Bottom, порядок Euler rotations или полную матрицу преобразования.**

## 4. Структура Exchange Package

Новый пакет с 3D-моделями:

```text
<package-id>/
├── manifest.json
├── board.snapshot.json
├── models/
│   └── models.json
├── assets/
│   └── 3d/
│       ├── <sha256>.step
│       └── <sha256>.x_t
└── checksums.sha256
```

Пакет без моделей продолжает иметь прежнюю структуру:

```text
<package-id>/
├── manifest.json
├── board.snapshot.json
└── checksums.sha256
```

### 4.1. Совместимость manifest

Сохранить:

```json
"schema": "ecad-mcad-bridge/package",
"schemaVersion": "1.0.0"
```

Не повышать версию manifest только из-за добавления необязательного каталога.

Добавить capability:

```text
component-3d-models
```

Правила:

- При наличии `models/models.json` capability обязателен.
- При наличии capability каталог `models/models.json` обязателен.
- Все файлы `models/models.json` и `assets/3d/*` должны присутствовать в `manifest.files`.
- Все файлы из `manifest.files` должны присутствовать в `checksums.sha256`.
- Сам `manifest.json` продолжает присутствовать в `checksums.sha256`, но не в `manifest.files`.
- `checksums.sha256` не включает сам себя.
- Старые пакеты без capability и без `models/models.json` должны читаться без ошибок.
- Каталог с моделями без соответствующего capability или capability без каталога — ошибка целостности пакета.

Никакого отдельного механизма контроля целостности для STEP/X_T не вводить: использовать единый механизм manifest/checksums.

## 5. Контракт `models/models.json`

Создать отдельную версионируемую схему:

```json
"schema": "ecad-mcad-bridge/component-models",
"schemaVersion": "1.0.0"
```

Она не должна менять версию схемы основного manifest.

Минимальная структура:

```json
{
  "schema": "ecad-mcad-bridge/component-models",
  "schemaVersion": "1.0.0",
  "components": [
    {
      "componentId": "component-id-from-board-snapshot",
      "designator": "U1",
      "bodies": [
        {
          "bodyOrdinal": 0,
          "representation": "generic",
          "sourceOrigin": "embedded",
          "assetAcquisition": "sdk-export",
          "assetFormat": "step-ap214",
          "assetPath": "assets/3d/<sha256>.step",
          "sdkOrigin": {
            "xIu": 1000000,
            "xMm": 2.54,
            "yIu": 2000000,
            "yMm": 5.08,
            "zIu": null,
            "zMm": null
          },
          "sdkState": {
            "rotationXDegRaw": 0,
            "rotationYDegRaw": 0,
            "rotationZDegRaw": 90,
            "dzIu": 393700,
            "dzMm": 1.0
          },
          "modelRotationDegRaw": 0
        }
      ]
    }
  ]
}
```

Это иллюстрация структуры, а не утверждение о фактических значениях API.

### 5.1. Связь с компонентом

`componentId` — точное значение `ComponentInstance.Id` из `board.snapshot.json`.

`designator` — контрольное и информационное поле. При чтении оно должно совпадать с designator связанного компонента.

Не использовать `SourceUniqueId` в качестве гарантированно стабильного ключа: его межсессионная стабильность не подтверждена.

В каталоге должна быть запись для каждого компонента платы. Если у компонента нет 3D-тел, `bodies` — пустой массив.

### 5.2. Несколько тел

Один компонент может иметь несколько `IPCB_ComponentBody`.

Каждое тело представляется отдельной записью `bodies[]`.

`bodyOrdinal` — нулевой ordinal внутри компонента, соответствующий порядку перечисления тел в конкретном экспорте.

Не объявлять `bodyOrdinal` глобально стабильным идентификатором между разными сессиями или версиями документа.

Не объединять несколько тел компонента в одну запись каталога.

### 5.3. Representation

Допустимые значения:

- `generic`
- `native`
- `unknown`

Это характеристика представления модели, а не формата экспортированного файла.

Не подменять неизвестный тип значением `generic` или `native`.

### 5.4. Source origin

Допустимые значения:

- `embedded`
- `native`
- `linked`
- `unknown`

Смысл:

- `embedded` — встроенная модель, если это подтверждено API.
- `native` — нативная процедурная/геометрическая модель Altium, если это подтверждено.
- `linked` — внешняя связанная модель, только если это подтверждено фактическим путём или другим надёжным признаком.
- `unknown` — недостаточно данных.

**`GetEmbed=false` само по себе не доказывает `linked`.**

По умолчанию при отсутствии доказательств использовать `unknown`.

### 5.5. Asset acquisition и формат

`assetAcquisition`:

- `sdk-export`
- `source-copy-verified`
- `not-acquired`
- `unknown`

`assetFormat`:

- `step-ap214`
- `parasolid-x_t`
- `null`, если asset не получен.

Правила:

- `sdk-export` означает, что файл получен через экспорт SDK.
- `source-copy-verified` разрешён только при доказанной побайтовой идентичности исходного файла и копии.
- Совпадение размера не доказывает идентичность.
- `not-acquired` означает, что геометрия тела известна, но файл для пакета не получен.
- `unknown` означает недостаточную информацию о способе получения.
- При отсутствии файла `assetPath` и `assetFormat` должны быть `null`.
- При наличии файла оба поля обязательны.

Не называть SDK-экспорт оригинальным исходным файлом модели.

### 5.6. Геометрия и placement metadata

STEP/X_T хранит геометрию тела. Метаданные каталога хранят сведения, необходимые для последующей интерпретации положения модели.

Не запекать в файл геометрии неподтверждённые преобразования компонента, модели или стороны платы.

В каталоге отдельно сохранять:

1. `sdkOrigin` — сырые X/Y/Z значения происхождения модели, полученные из API; каждую линейную величину хранить парой IU/mm.
2. `sdkState` — сырые углы `GetState` и `dz`; `dz` обязательно хранить парой IU/mm.
3. `modelRotationDegRaw` — отдельное nullable-поле для `GetRotation`, если значение доступно.

Для `sdkOrigin`:

- X и Y сохранять в IU и мм.
- Z, если API не предоставляет подтверждённого значения, оставлять `null` одновременно в IU и мм.
- Не подставлять ноль вместо неизвестного значения.

Для `sdkState`:

- Сохранять исходные значения углов без нормализации.
- Значение 360° не заменять на 0° в сохранённых raw-данных.
- Линейную составляющую `dz` сохранять как `dzIu` и `dzMm`.
- Не интерпретировать знак, порядок применения углов и направление осей сверх подтверждённого.

Положение компонента на плате уже содержится в `board.snapshot.json`: не дублировать его в каталоге без необходимости. При последующем чтении связь устанавливается через `componentId`.

Каталог должен явно документировать, что сырые значения API ещё не образуют подтверждённую полную матрицу `T_B_S`.

## 6. Хранение 3D-файлов

### 6.1. Content-addressed paths

Хранить файлы по содержимому:

```text
assets/3d/<lowercase-sha256>.step
assets/3d/<lowercase-sha256>.x_t
```

SHA-256 вычисляется по фактическим байтам файла, который помещается в пакет.

Правила:

- Только lowercase SHA-256 в имени файла.
- Расширение должно соответствовать `assetFormat`.
- Один и тот же asset одного формата должен храниться один раз, даже если на него ссылаются несколько тел.
- Один asset может использоваться несколькими компонентами.
- Два разных файла с одинаковым именем и разным содержимым недопустимы.
- Абсолютный путь исходного файла в каталог не попадает.
- В пакет не помещаются исходные файлы, если они не были явно переданы Writer.

### 6.2. Writer API

Расширить существующий Writer типизированным API для передачи каталога и файлов моделей.

Сохранить существующие публичные вызовы `ExchangePackageWriter.Write`, используемые текущими тестами и Altium Add-in.

Новый API должен позволять передать:

- каталог моделей;
- набор входных STEP/X_T файлов;
- связь тел каталога с переданными файлами.

Не заставлять вызывающий код заранее вычислять SHA-256, размер или конечный путь в пакете.

Writer сам:

1. Проверяет входные метаданные и исходные файлы.
2. Вычисляет SHA-256 и размер.
3. Создаёт content-addressed относительные пути.
4. Формирует `models/models.json` с уже разрешёнными путями.
5. Добавляет каталог и все ассеты в manifest и checksums.
6. Пишет файлы во временный каталог.
7. Проверяет записанные файлы.
8. Атомарно публикует пакет через существующий механизм `Directory.Move`.

Допускается выбрать подходящий набор DTO/request-классов, но публичный контракт должен оставаться типизированным и CAD-независимым.

### 6.3. Потоковая обработка

3D-файлы могут иметь большой размер.

Запрещено читать STEP/X_T целиком через `File.ReadAllBytes` для вычисления SHA-256 или копирования.

Использовать потоковую обработку:

- потоковое чтение и вычисление SHA-256;
- потоковое копирование в staging directory;
- подсчёт размера в `long`;
- проверка исходного файла до и после чтения/копирования;
- проверка, что файл не изменился во время операции;
- потоковая проверка SHA-256 при чтении пакета.

Хеш должен относиться к тем же байтам, которые фактически записаны в staging directory. Не делать отдельный предварительный hash, а затем независимое копирование без контроля изменения файла.

Адаптировать `PackageChecksums.ComputeFileSha256` и при необходимости `PackageFileHasher.ComputeStableSha256`, чтобы не использовать неограниченное выделение памяти для больших файлов.

Синхронная реализация допустима в рамках существующего API; не блокировать UI-поток новым кодом Altium — он здесь не реализуется.

## 7. Reader и валидация

Расширить `ExchangePackageReader.Read`.

Результат чтения должен предоставлять типизированный каталог моделей, например `ModelCatalog`/`ComponentModels`, nullable для старого пакета без 3D-моделей.

Reader не должен загружать STEP/X_T в память целиком и не должен пытаться интерпретировать геометрию CAD.

### 7.1. Проверки каталога

Проверять:

- JSON синтаксис и UTF-8;
- schema name и major version каталога;
- обязательные поля;
- допустимые значения enum;
- уникальность `componentId`;
- наличие каждого `componentId` в `board.snapshot.json`;
- совпадение `designator`;
- отсутствие повторного `bodyOrdinal` внутри одного компонента;
- согласованность `assetAcquisition`, `assetFormat` и `assetPath`;
- парность IU/mm: оба значения либо заполнены, либо оба `null`;
- корректность raw numeric значений: запрет `NaN` и `Infinity`;
- отсутствие невалидных или дублирующихся ссылок на файлы.

Проверка каталога должна выполняться после базовой проверки файлов manifest/checksums и до успешного результата `PackageReadResult`.

### 7.2. Проверки ассетов

Для каждого тела с `assetPath`:

- путь безопасен и относителен;
- файл присутствует в manifest;
- файл присутствует в checksums;
- файл существует на диске;
- SHA-256 совпадает с manifest и checksums;
- размер совпадает с manifest;
- расширение соответствует `assetFormat`;
- имя файла соответствует фактическому SHA-256;
- файл расположен в `assets/3d/`.

Проверить также обратную связь:

- каждый файл в `assets/3d/` должен быть указан в каталоге моделей;
- не должно быть неиспользуемых и потерянных ассетов;
- повторяющиеся ссылки на один content-addressed файл разрешены;
- разные файлы не должны конфликтовать по пути, в том числе с учётом регистра имён на Windows.

Сохранить существующие проверки extra files, missing files, checksum mismatch, size mismatch, path traversal и reparse points/symlinks.

### 7.3. Ошибки

Добавить стабильные диагностические коды `EMB-PKG-*` для ошибок каталога и ссылок на 3D-ассеты.

Не использовать исключения как обычный механизм валидации.

В сообщениях об ошибках не раскрывать абсолютные пути исходных пользовательских моделей.

## 8. Детерминизм

Соблюдать существующие правила:

- UTF-8 без BOM;
- LF;
- invariant culture;
- фиксированный порядок JSON-полей;
- детерминированная сортировка;
- lowercase SHA-256;
- стабильный порядок моделей и тел.

Рекомендуемый порядок:

- компоненты — по `componentId`, ordinal;
- тела — по `bodyOrdinal`;
- файлы — по относительному пути, ordinal.

Повторная сериализация одного и того же каталога при одинаковых входных данных должна давать идентичные байты.

Не включать время создания файла, абсолютные исходные пути или случайные GUID в `models.json`.

## 9. Тесты

Расширить `tests/EcadMcadBridge.Core.Tests/ExchangePackageTests.cs` и при необходимости добавить отдельные тестовые классы.

Обязательные тесты:

### 9.1. Обратная совместимость

- Старый пакет без 3D-каталога успешно читается.
- Старый публичный Writer API продолжает работать.
- Manifest остаётся `1.0.0`.
- Пакет без 3D-моделей не получает capability `component-3d-models`.
- Для старого пакета `ModelCatalog == null`.

### 9.2. Round-trip

- Запись и чтение каталога.
- Несколько компонентов.
- Несколько тел у одного компонента.
- Компонент с пустым `bodies`.
- Общий asset, на который ссылаются несколько тел.
- STEP и X_T одновременно.
- Сохранение `sourceOrigin`, `representation`, `assetAcquisition`.
- Сохранение неизвестных значений как `unknown`/`null`.
- Сохранение исходного угла 360° без нормализации.
- Сохранение IU/mm без потери точности.

### 9.3. Целостность

Проверить отказ Reader при:

- отсутствии `models/models.json`;
- отсутствии capability при наличии каталога;
- capability без каталога;
- отсутствующем asset-файле;
- изменённом содержимом asset;
- неверном SHA-256;
- неверном размере;
- неверном расширении;
- пути `../`, абсолютном пути, `\` и `:`;
- ссылке на файл, отсутствующий в manifest;
- файле assets/3d, не указанном в каталоге;
- некорректном JSON;
- неподдерживаемой major version;
- неизвестном `componentId`;
- несовпадающем designator;
- повторных `bodyOrdinal`;
- повторных `componentId`;
- case-insensitive конфликте путей.

### 9.4. Потоковая обработка и атомарность

Проверить:

- потоковое копирование синтетического файла размером, существенно превышающим размер snapshot;
- потоковое вычисление SHA-256;
- Writer не оставляет частичный опубликованный пакет при ошибке;
- Writer не перезаписывает существующий package-id;
- временный каталог очищается после неуспешной записи;
- файл, изменившийся во время копирования, отклоняется.

Тесты не должны зависеть от установленного Altium или SOLIDWORKS.
