# DECISIONS — ECAD-MCAD Bridge

Архитектурные решения в формате ADR. Изменение архитектуры без записи здесь запрещено.

Статусы: `Accepted` — действует; `Proposed` — требует решения; `Superseded` — заменено;
`Rejected` — отклонено.

## D-001 — Два CAD Add-in и общая библиотека Core

**Статус:** Accepted (согласовано до bootstrap).

**Контекст.** Нужна интеграция Altium Designer и SOLIDWORKS. Прямые ссылки между CAD SDK
создают связность, конфликты версий и невозможность тестировать логику без обеих CAD-систем.

**Решение.** Система состоит из:

- `EcadMcadBridge.Altium` — Add-in Altium;
- `EcadMcadBridge.SolidWorks` — Add-in SOLIDWORKS;
- `EcadMcadBridge.Core` — общая библиотека модели, валидации и формата обмена.

Add-in ссылаются на Core и только на SDK своей CAD-системы. Add-in не ссылаются друг на друга.

**Последствия.**

- Core тестируется без CAD.
- Появляется необходимость версионировать контракт Core.
- Усложняется сборка (несколько проектов), но упрощается развитие.

**Запрещено.** Размещать код SOLIDWORKS в Altium Add-in или наоборот; добавлять CAD SDK в Core.

## D-002 — Согласованный стек

**Статус:** Accepted (согласовано до bootstrap).

**Контекст.** Нужна однозначная база, чтобы избежать смешения версий и API.

**Решение.**

| Компонент | Значение |
|---|---|
| Altium Designer | 26 |
| Altium SDK | 4.0.1 |
| .NET SDK | 10 |
| Target Framework | `net10.0-windows` |
| Язык | C# |
| SOLIDWORKS | 2026 |

**Последствия.**

- Все проекты решения используют `net10.0-windows`; исключения требуют нового ADR.
- API-контракт фиксируется по SDK 4.0.1; конкретные reference assemblies — V-02.
- Установленный .NET SDK 11 не используется для сборки проекта.

**Риск.** AD26 может не загружать `net10.0-windows` in-process. Это проверяется в `BRIDGE-000001`;
при отрицательном результате требуется новый ADR, а не самовольное понижение TFM (D-013).

## D-003 — Запрет DelphiScript и Legacy API

**Статус:** Accepted (согласовано до bootstrap).

**Контекст.** Altium исторически поддерживает DelphiScript и старые API, которые несовместимы
с современным SDK и усложняют поддержку.

**Решение.** Запрещено использовать DelphiScript и Legacy API Altium. Разрешены только
интерфейсы Altium SDK 4.0.1, подтверждённые в `SDK_API_LEDGER.md`.

**Последствия.**

- Часть примеров и готовых решений отбрасывается.
- Требуется документировать каждую сигнатуру.
- Код становится переносимее между версиями AD.

---

## D-004 — SOLIDWORKS вне текущего scope

**Статус:** Accepted (согласовано до bootstrap).

**Контекст.** Требуется сначала стабилизировать ECAD-сторону и контракт Core.

**Решение.** На текущем этапе не реализуется функциональность обмена с SOLIDWORKS:
нет проекта Add-in, нет interop-ссылок, нет импорта/экспорта в SOLIDWORKS.

**Последствия.**

- Контракты Core проектируются нейтрально, но проверяются только на Altium-данных.
- Появление SOLIDWORKS-кода требует отдельного ТЗ и ADR.
- Риск «подстроить Core под Altium» снижается ревью контрактов.

---

## D-005 — Нейтральный Core и версионируемый пакет

**Статус:** Accepted.

**Контекст.** Add-in не должны знать детали реализации друг друга.

**Решение.** Обмен идёт через Exchange Package (JSON + контрольные суммы) с явной версией схемы.
Core владеет моделью и форматом; Add-in только преобразуют свои данные в/из Core.

**Последствия.**

- Формат можно проверять и тестировать отдельно.
- Несовместимые изменения требуют major-версии схемы.
- Появляется стоимость сериализации и валидации, но растёт надёжность.

---

## D-006 — Файловый протокол с локальным агентом через Git

**Статус:** Accepted.

**Контекст.** Локальный агент работает на CAD-стенде; нужен простой, аудируемый и не сетевой
способ передавать задачи и результаты.

**Решение.** Единственные каналы — `.agent/tasks/`, `.agent/reports/`, `.agent/reviews/` в Git.
Формат — Markdown с YAML front matter. Жизненный цикл, ветки и правила — в `ARCHITECTURE.md`, раздел 8.

**Последствия.**

- Все действия агента аудируемы через историю Git.
- Нет прямого API и сетевого сервиса.
- Требуется дисциплина именования и статусов.
- Конфликты решаются через Git, а не через блокировки.

## D-007 — Политика доказанности API

**Статус:** Accepted.

**Контекст.** Неподтверждённые сигнатуры приводят к падениям в CAD-хосте и ложной уверенности.

**Решение.** API считается подтверждённым только при наличии доказательства: исходник SDK 4.0.1,
метаданные сборки или успешный smoke-тест. Всё остальное — «Требует проверки».
Reflection и `dynamic` — временный обход, а не API.

**Последствия.**

- `SDK_API_LEDGER.md` становится обязательным артефактом каждого PR с кодом.
- Скорость разработки ниже, но предсказуемость выше.
- Некоторые удобные, но недокументированные вызовы запрещены.

## D-008 — Bootstrap-этап только документация

**Статус:** Accepted.

**Контекст.** `BRIDGE-BOOTSTRAP-001` инициализирует проект; смешивание с реализацией размывает приёмку.

**Решение.** В рамках bootstrap создаются только документы и структура каталогов.
Код Add-in/Core/тестов не создаётся; он входит в `BRIDGE-000001`.

**Последствия.**

- PR содержит только Markdown и служебные `.gitkeep`.
- Проверка структуры и ссылок выполняется без сборки.
- Первый технический PR будет отдельным.

## D-009 — Единицы и координаты обмена

**Статус:** Accepted.

**Контекст.** Altium хранит координаты в целочисленных единицах, SOLIDWORKS — в метрах/миллиметрах;
без явного соглашения неизбежны ошибки масштаба.

**Решение.**

- В пакете — миллиметры, точность не хуже `1e-6`.
- Координаты: правая декартова система, X вправо, Y вверх, начало — начало координат платы Altium.
- Поворот: против часовой стрелки, градусы, `[-180, 180)`.
- Сторона: `top`/`bottom`; исходный `layerId` сохраняется.
- Преобразование Altium Coord ↔ мм — через `EDP.Utils` (подтверждено).

**Последствия.**

- Все конвертеры обязаны иметь тесты на округление и знак.
- При появлении SOLIDWORKS-стороны преобразование в её систему координат выполняется в adapter,
  а не в Core.

## D-010 — Политика стабильных идентификаторов

**Статус:** Proposed.

**Контекст.** Для сопоставления ECAD/MCAD нужен ID, устойчивый к переименованиям и повторному экспорту.

**Предложение.**

1. Использовать `SourceUniqueId`, если он непуст и стабилен.
2. Иначе — SHA-256 от нормализованного `designator|footprint|side|layerId|x|y|rotation`.
3. Коллизии разрешать суффиксом `#2`, `#3`, … с предупреждением.

**Почему Proposed.** Стабильность `SourceUniqueId` между ECO не проверена (V-07).
До проверки нельзя обещать стабильность ID.

**Как принять.** Провести эксперимент в `BRIDGE-000001`, зафиксировать результат,
перевести в `Accepted` или изменить правило.

## D-011 — Запрет проприетарных бинарников в репозитории

**Статус:** Accepted.

**Контекст.** SDK и CAD-сборки проприетарны; их коммит создаёт юридические и размерные риски.

**Решение.** В репозитории не хранятся `Altium.SDK*.dll`, `Altium.Controls*.dll`, `DevExpress*.dll`,
`SolidWorks.Interop*.dll`, лицензии и установщики CAD. Ссылки — через настраиваемые пути.

**Последствия.**

- Сборка требует установленного CAD/SDK на агенте.
- CI должен иметь способ получить SDK легально либо не собирать Add-in.
- Версии фиксируются в документации, а не бинарниками.

---

## D-012 — Только PR в `source`

**Статус:** Accepted.

**Контекст.** `source` — базовая ветка; прямой push разрушает аудит.

**Решение.** Любое изменение попадает в `source` только через Pull Request.
Автор не мержит собственный PR без независимой проверки; исключение для bootstrap — по решению Оператора.

**Последствия.**

- История `source` линейна и проверяема.
- Требуется review-файл или явный approve.
- Агент не может самостоятельно «завершить» задачу — только подготовить PR.

---

## D-013 — TFM не меняется молча

**Статус:** Accepted.

**Контекст.** Согласованный TFM — `net10.0-windows`, но совместимость с AD26 не проверена.

**Решение.** Если `net10.0-windows` не работает в AD26, исполнитель обязан:

1. остановить работу;
2. зафиксировать `blocked` и доказательства;
3. предложить варианты (например, `net8.0-windows` только для Altium Add-in);
4. дождаться ADR.

Понижение TFM без ADR запрещено.

**Последствия.**

- Возможен простой в работе, но архитектура остаётся управляемой.
- Решение о разных TFM для Altium/SOLIDWORKS будет отдельным ADR.

## Процесс изменения решения

1. Предложение оформляется как новый ADR или изменение существующего в PR.
2. Указываются контекст, альтернативы, последствия и влияние на существующие документы.
3. Решение принимает Оператор; статус меняется на `Accepted`.
4. Заменённое решение получает `Superseded` и ссылку на новое.
5. Затронутые документы (`ARCHITECTURE.md`, `DEVELOPMENT_RULES.md`, `SDK_API_LEDGER.md`) обновляются
   в том же PR.
6. Исполнитель не может самостоятельно принять архитектурное решение, только предложить.
